## 1. 结论

在服务单下面加一层“巡检次”（`ServiceVisit`），把排期、进度、交付和验收从服务单移到巡检次上，再加付款节点。只有 1 次巡检的服务单，状态和行为与现在一样，所以现有链路不用推倒。

分三段做：

| 阶段 | 做什么 | 依赖 | 完成后的结果 |
| --- | --- | --- | --- |
| A 契约与服务端 | 契约 2.0.0、迁移、状态机、服务商 API、字段调整 | nav-plan-c 已提交 | 用 API 能走完 6 次巡检和按次验收，不收钱 |
| B 页面 | M05–M08 和“我的”改为多次巡检 | A | App 上能走完，付款区块隐藏 |
| C 接付款 | 打开付款节点，接统一交易模块 | 支付渠道、收款主体已定；交易模块完成支付回执 | 首付、按次付款、已完成判定生效 |

不变的部分：M01–M04、登录和权限码、文件扫描和 MinIO 私有存储、幂等机制、方案版本规则、方案确认前取消。

不做的部分：不新增结算状态（AGENTS.md §11、D9）；巡检模块不直连支付渠道（AGENTS.md §3）；不建服务商工作台页面；不建 APP-ORD-02 服务订单详情页（§7）。

## 3. 目标模型

### 3.1 对象关系

```text
预约 Reservation
└─ 方案 ServicePlan（版本化，确认后不变）
   ├─ 计划巡检 PlanVisit × N（第几次、计划日期）
   └─ 付款节点 PaymentNode × (N+1)（首付 + 每次一笔，金额快照）

服务单 ServiceOrder（确认方案时创建，从方案复制巡检次和付款节点）
├─ 人员与设备 Assignment（全单共用）
├─ 付款节点（只记金额和是否已付；是否已付只由交易模块回写）
└─ 巡检次 ServiceVisit × N
   ├─ 进度 ProgressEvent
   ├─ 交付 Delivery × 0..1 → 文件
   └─ 验收 Acceptance × 0..1
```

### 3.2 状态

巡检次是新状态：

```text
PENDING_SCHEDULE（待排期）→ SCHEDULED（已排期）→ IN_PROGRESS（作业中）→ DELIVERED（已交付待验收）→ ACCEPTED（已验收）
```

方案上的日期是计划日期；服务商确认具体开始时间后才算已排期，这与画布“第 2 次已排期，其余待排期”一致。

服务单的枚举不变，含义改为由巡检次推导：

| 状态 | 新含义 | 1 次巡检时 |
| --- | --- | --- |
| `ARRANGING` | 确认方案后，第 1 次开工前 | 与现在相同 |
| `IN_PROGRESS` | 第 1 次开工后，全部交付前 | 与现在相同 |
| `DELIVERED` | 全部已交付，还有未验收的 | 与现在相同 |
| `ACCEPTED` | 全部已验收 | 与现在相同 |

“已完成”要求全部验收并结清，但 D9 不允许新增结算状态，所以不加服务单状态，只在列表阶段里计算：

| 画布状态 | 服务单 | 巡检次 | 付款 | 列表阶段 `stage` |
| --- | --- | --- | --- | --- |
| 待报价 | 无 | 无 | 无 | `AWAITING_PLAN` |
| 待确认 | 无 | 无 | 无 | `AWAITING_CONFIRMATION` |
| 待履约 · 待付首付 | `ARRANGING` | 未开工 | 首付未付 | `AWAITING_PAYMENT`（阶段 C 新增） |
| 待履约 | `ARRANGING` | 未开工 | 首付已付 | `IN_PROGRESS` |
| 履约中 | `IN_PROGRESS` | 没有待验收的 | 任意 | `IN_PROGRESS` |
| 履约中 · 第 n 次待验收 | `IN_PROGRESS` | 第 n 次 `DELIVERED` | 任意 | `AWAITING_ACCEPTANCE` |
| 待验收 | `DELIVERED` | 全部已交付 | 任意 | `AWAITING_ACCEPTANCE` |
| 全部验收，未结清 | `ACCEPTED` | 全部 `ACCEPTED` | 有未付 | `AWAITING_PAYMENT`（阶段 C 新增） |
| 已完成 | `ACCEPTED` | 全部 `ACCEPTED` | 全部已付 | `COMPLETED` |

规则：
- 有待验收的巡检次就算待验收，优先于待付款。这样“我的”和订单中心的“待验收”筛选能看到第 1 次待验收的单子，与画布一致；订单主状态仍是履约中。
- `payment_mode=NONE` 的服务单不看付款列，全部验收即 `COMPLETED`。阶段 A、B 的服务单和存量服务单都是这种情况。

### 3.3 规则

1. 服务单状态只由服务端在同一事务里推导，客户端不能指定。
2. 按次序开工：上一次有 `SERVICE_COMPLETED` 后，下一次才能 `SERVICE_STARTED`。
3. 每次巡检只有一次交付和一次验收；重复命令幂等返回。验收后不可撤销。
4. 并发：针对巡检次的命令用巡检次的 ETag，服务单 ETag 只管服务单自身字段，同一服务单的命令用行锁串行。否则客户验收第 1 次和服务商推进第 2 次会互相报版本冲突。
5. 幂等：请求摘要加入 `visitId`。现在 `digestProgress` 等摘要不含资源 ID，改为多次后同样的内容会串到另一次。
6. 审计：`inspection_state_transition` 增加 `SERVICE_VISIT`，巡检次每次迁移写一条。
7. 阶段 C 起，付款节点模式的服务单必须首付已付才能开工第 1 次；排期和人员安排可以提前做。

## 9. 付款节点与统一交易模块

### 9.1 先后顺序

建议先改巡检模型，再建交易模块，最后接付款：

1. 阶段 A、B 把付款节点的模型和计算做好，开关默认关闭。开关关闭时方案不生成节点，服务单 `payment_mode=NONE`，页面不显示付款区块，不把未接入的能力展示出来（AGENTS.md §3）。
2. 交易模块按概要设计 P2 建，先完成支付回执这部分。这部分不依赖商品，巡检和商城共用。
3. 阶段 C 打开开关。之前创建的服务单仍是 `NONE`，不受影响。

### 9.2 职责边界

| 巡检模块 | 统一交易模块 |
| --- | --- |
| 计算和保存节点金额快照 | 生成付款单，对接渠道 |
| 判断节点是否可付：首付在确认后可付，按次在该次验收后可付 | 校验回执金额、处理重复通知、保存回执 |
| 首付未付时拒绝开工 | 收银台、支付结果页 |
| 用 `paid_at` 记录交易模块回写的结果，用于列表和判定 | 退款、对账导出（D2） |

`paid_at` 只能由交易模块回写，巡检模块和客户端都不能自己标记已付（AGENTS.md §11）。

### 9.3 回写方式

现在的 `inspection_domain_event_outbox` 只写入，没有任何代码投递这些事件，所以不能靠它传递付款结果。

建议交易模块处理完回执后，在同一进程内调用巡检模块的应用服务回写，以回执 ID 做幂等键；失败由交易模块重试。两个模块不读对方的表（AGENTS.md §5）。
