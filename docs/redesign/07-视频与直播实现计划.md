# 发现页视频与直播实现计划（2026-11-20）

> 起因：用户 2026-11-20 指出“原型中有视频和直播在发现中，为什么没做，需要做”。
> 依据：2026-11-14 修订版原型 `.planning/prototype/v2-20261114`：`Discover`（七个频道：推荐 / 视频 / 直播 / 赛事 / 研学 / 案例 / 知识）、`VideoFeed`（竖屏视频流）、`ContentVideo`（视频内容详情）、`LiveNotice`（直播预告与回看入口）、`LiveRoom`（直播间）。
> 范围依据：概要设计 §7.6、§14 D19（已确认：竖屏视频流和平台内直播观看端进一期，直播间不收款、不做打赏）、D20（① 已确认：推流与播放接第三方直播服务，经适配器接入，不自研；②–⑤ 未定）。

## 1. 为什么之前没做

H1（发现页图文）开工时，我把视频和直播一并写成“D19、D20 未定，不做”（AGENTS §2 M19）。这是错的：D19 在 2026-11-13 已确认视频和直播进一期；只有直播的服务商和 D20 ②–⑤ 没定。视频不依赖这些，本来就该做；直播可以先按适配器加本机模拟服务做出观看端（和微信支付先用模拟服务的做法一样），未定的事项写成设计假设。

## 2. 视频（V，扩展 M19 `content`）

- 内容加类型 `VIDEO`：封面、时长、竖屏/横屏、播放地址（服务端只给受控 HTTPS 地址；开发环境没有视频存储，预览构建按内容 ID 用 App 内的示例视频，示例视频由画板图片合成，不用外部素材）。
- 视频挂一个入口（商品 / 服务 / 活动 / 场馆，按稳定 ID，沿用“内容中提到”）。
- 读：发现页“视频”频道、推荐瀑布流里的视频卡（时长角标）、视频详情 `ContentVideo`、竖屏视频流 `VideoFeed`（上下切换，按发布时间和运营排序，不做推荐算法）。
- 写（要登录）：点赞、关注发布者（机构）、评论。评论设计假设见 §4。收藏不做（“收藏与对比”仍未确认）。

## 3. 直播（L，新模块 M20 `live`）

- 直播间：主办机构、标题、封面、预告时间、状态（预告 / 直播中 / 已结束）、讲解清单（商品 / 服务 / 活动，按稳定 ID）、合作平台回看链接（可选）。
- 推流与播放：`LiveStreamProvider` 端口；开发用本机模拟服务（给出推流地址和一个循环播放的示例视频作为播放地址，可模拟“开播 / 断流 / 结束”回调）。真实服务商选定前不接任何第三方 SDK。
- 读：发现页“直播”频道和直播条、直播预告页 `LiveNotice`（设提醒、回看入口）、直播间 `LiveRoom`（画面、弹幕、点赞、关注主播、讲解清单）。
- 写（要登录）：设提醒（开播时记一条站内信“直播提醒”）、发弹幕、点赞、关注主播。直播间不收款、不做打赏；讲解清单进平台内现有详情页。
- 开播端：不做页面。主办机构经受权接口建直播间、改预告；开播和结束以服务商回调为准（开发用模拟服务的控制接口）。

## 4. 设计假设（D20 ②–⑤ 未定前先这样做，可改）

1. 谁能开播：平台给机构开通直播权限（机构角色），没有开通的不能建直播间。
2. 主播怎么开播：用服务商提供的推流工具（App 不做开播端）。
3. 弹幕和评论：只有登录账号能发；单条 ≤ 50 字（弹幕）/ ≤ 200 字（评论）；同一账号限频；过关键词过滤后直接显示；平台客服和主办机构经受权接口可隐藏单条；用户可举报（记到客服反馈）。审核由谁负责仍待定。
4. 资质与备案：未确认前直播和视频只在预览构建显示，公开构建的发现页保持原样（和 M19 一样）。

## 5. 验证

L3：后端全量、App 全量单测与类型检查、开发版 E2E（新增视频和直播用例，直播用模拟服务开播）、公开版防泄漏、390 宽对照图逐张看。
