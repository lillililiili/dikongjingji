# 08｜已确定事项与待确认项

## 1. 已确定

| 事项 | 决定 |
| --- | --- |
| 产品性质 | 正式产品，分阶段开发 |
| 当前增量 | 只做 M01 与 M02 |
| 移动端 | Android、iOS 真机 |
| 微信小程序 | 未来开发，本期不做 |
| 移动端技术 | uni-app + Vue3 + TypeScript + Pinia |
| 后端 | Java21 + Spring Boot3.5 |
| 数据库 | PostgreSQL + PostGIS |
| 开发形式 | 模块化单体 |
| UI风格 | 面向公众、生活服务化，不做政务/大屏 |
| 主色 | 橙色 |
| 首批城市 | 东营作为首发配置，但不得硬编码 |
| 城市状态 | 两页共享，列表不得自动变济南 |
| 分类编码 | 使用稳定英文编码 |
| 油气/燃气 | 稳定编码 OIL_GAS，默认展示“油气” |
| 目录浏览 | 默认允许未登录浏览 |
| 服务卡语义 | 平台标准化服务项目，不是某个服务商独立商品 |
| 评分/次数 | 只显示真实数据，无数据隐藏 |
| 后续动作 | 类型化宿主端口 + 生产功能开关 |
| 数据访问 | App 只访问 HTTPS API，不直连数据库 |

## 2. 本期默认但可配置

- M01 场景顺序。
- Hero 文案和图片。
- 服务保障项。
- 服务流程项。
- 热门服务。
- 分类展示名和副标题。
- 服务卡主动作文字。
- 价格模式。
- 是否开放距离排序。

这些内容不得散落硬编码在页面；开发 Fixture 只能用于测试。

## 4. 正式数据待确认

这些事项不阻塞静态 UI，但阻塞生产数据发布：

1. 首批真实服务名称。
2. 每项服务的正式价格模式和价格。
3. 东营首批真实可服务范围。
4. 正式图片及授权。
5. 哪些服务可立即咨询、哪些只可预约。
6. 服务保障文案是否有真实制度和能力支撑。
7. 服务完成数和评分的统计来源。
8. 是否允许匿名搜索全部目录。
9. 距离是到覆盖区域、服务商还是作业中心。
10. 目录数据的维护责任人和后台上线时间。

## 5. 进入 I2 前必须决定

- 服务详情是平台标准服务详情，还是具体服务商商品详情。
- 用户是先选服务再发需求，还是可直接发布非标需求。
- “立即咨询”和“预约”的统一业务动作。
- 一个需求是否允许多服务商报价。
- 普通用户与企业用户可见服务是否不同。
- 登录、认证和联系方式获取时点。

## 6. 不允许 Codex 自行决定

- 在线支付、保证金、退款、发票、结算和抽佣。
- 自动派单、抢单和动态定价。
- 飞手和服务商认证规则。
- 空域审批和飞行控制。
- 将参考图数据直接当正式数据。
- 改动一级导航。
- 把管理后台、本期目录和完整交易闭环合并一次开发。
