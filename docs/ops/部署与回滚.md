# 生产部署、发布与回滚（S2-4）

> 建立：2026-11-22（计划 `docs/redesign/08-后续开发计划.md` S2-4）。
> 现状：部署文件都在 `infra/prod/`，**没有在任何真实服务器上跑过**；服务器、域名、证书和部署方式都等你提供或决定。下面的路径、域名都是占位，照着换成真实的。
> 本地验证过的：`docker compose -f infra/prod/docker-compose.yml config` 语法（用一份临时的假值环境文件）；备份脚本和恢复脚本的 `--check`、`--into` 在本机起的 postgis 容器上跑通（备份、校验、恢复后 PostGIS 数据一致）。没验证的：nginx 配置（本机没有 nginx 镜像，没有拉取）、`--replace-production`、证书、真实域名。

## 1. 部署形态

一台 Linux 服务器（建议 4 核 8 GB 内存、100 GB 系统盘 + 单独一块数据盘起步），Docker + Docker Compose，全部服务在一个 compose 项目里：

| 容器 | 镜像 | 对外 | 作用 |
| --- | --- | --- | --- |
| `nginx` | `nginx:1.27-alpine` | 80、443 | HTTPS 终止和反向代理；H5 静态站点 |
| `backend` | 由 `backend/Dockerfile` 构建，`low-altitude/backend:<提交号>` | 无 | Spring Boot 后端（Java 21），启动时自动跑各模块的 Flyway 迁移 |
| `postgres` | `postgis/postgis:16-3.5` | 无 | 主库 |
| `redis` | `redis:7.2.4-alpine` | 无 | 只做缓存、限流、请求去重（有密码） |
| `minio` | `minio/minio:RELEASE.2025-04-22T22-12-26Z` | 控制台只绑 `127.0.0.1:9001` | 对象存储：巡检预约附件、交付文件（`<环境名>-inspection-*` 私有桶）；资质附件、服务订单交付文件、导入文件、售后凭证（`<环境名>-platform-private` 私有桶）；已授权的展示图、运营素材、商品图片（`<环境名>-public-assets` 桶，匿名只读） |
| `minio-init` | `minio/mc:…` | 无 | 每次启动时建桶、设权限，跑完退出 |

三个域名（同一张证书，SAN 或通配符）：

| 变量 | 例子 | 指向 |
| --- | --- | --- |
| `LA_API_DOMAIN` | `api.<你的域名>` | `/api/` → 后端；`/healthz` → 后端健康检查；微信支付回调也在这里 |
| `LA_H5_DOMAIN` | `m.<你的域名>` | H5 静态站点（也是后端允许的跨域来源） |
| `LA_FILES_DOMAIN` | `files.<你的域名>` | MinIO：预签名上传下载地址按它签名；`<环境名>-public-assets` 桶的图匿名可读 |

服务器上的目录：

```text
/opt/low-altitude/                 仓库代码（只读部署用，git checkout 到发布的提交）
/etc/low-altitude/prod.env         环境变量（600，root）；样例 infra/prod/.env.example
/etc/low-altitude/tls/             fullchain.pem、privkey.pem
/etc/low-altitude/secrets/wechat/  apiclient_key.pem、pub_key.pem（docs/ops/微信支付联调清单.md）
/etc/low-altitude/secrets/bootstrap/  首个平台运营账号的一次性口令文件（§3.1，用完删掉，平时是空的）
/srv/low-altitude/data/            postgres/、redis/、minio/（数据盘）
/srv/low-altitude/backups/db/      数据库备份（最好另一块盘，再拷到异地）
/srv/low-altitude/web/             releases/<版本>/、current → releases/<版本>（H5）
/srv/low-altitude/acme/            证书续期的 HTTP-01 验证目录
/var/log/low-altitude/             备份等脚本的日志
```

## 2. 要你准备或决定的

1. 服务器（云厂商、规格、地域）和登录方式（只用 SSH 密钥）。
2. 域名和 ICP 备案（大陆服务器上的网站和 App 接口要备案；App 上架还要 App 备案）。
3. HTTPS 证书：买的证书，或用 ACME（如 certbot、acme.sh）自动签。自动签的话 HTTP-01 验证目录已经在 nginx 里留好（`/srv/low-altitude/acme`）。
4. 部署方式：直接在服务器上构建镜像（本文按这个写），还是 CI 构建后推到你们的镜像仓库再拉。
5. 备份的异地去处（对象存储桶或另一台机器）。

## 3. 首次部署

```sh
# 1. 目录和权限
sudo mkdir -p /etc/low-altitude/tls /etc/low-altitude/secrets/wechat /etc/low-altitude/secrets/bootstrap \
  /srv/low-altitude/{data,backups/db,web/releases,acme} /var/log/low-altitude
sudo cp infra/prod/.env.example /etc/low-altitude/prod.env && sudo chmod 600 /etc/low-altitude/prod.env
sudo vi /etc/low-altitude/prod.env          # 逐项填值（随机值用 openssl rand -base64 32）
sudo cp infra/prod/logrotate/low-altitude /etc/logrotate.d/low-altitude

# 2. 证书放到 /etc/low-altitude/tls/（fullchain.pem、privkey.pem，privkey 权限 600）

# 3. 检查 compose 能展开（缺哪个变量会直接报名字）
cd /opt/low-altitude
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml config -q

# 4. 构建后端镜像，标签用提交号，写进 prod.env 的 LA_BACKEND_TAG
TAG=$(git rev-parse --short HEAD)
sudo sed -i "s/^LA_BACKEND_TAG=.*/LA_BACKEND_TAG=$TAG/" /etc/low-altitude/prod.env
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml build backend

# 5. 放 H5（见 §7 的发布步骤），然后起全部服务
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml up -d
sudo infra/prod/check-health.sh
```

注意：

- 后端用 `SPRING_PROFILES_ACTIVE=prod`，**不要用 dev**：dev 会灌开发账号和示例数据、打开开发控制接口。生产库里不该有开发种子。
- 后端在 nginx 后面，按 `X-Forwarded-For` 认客户端地址（`SERVER_FORWARD_HEADERS_STRATEGY=native`，只信内部网络的代理；nginx 只传真实的客户端地址）。城市搜索的限流按它算。
- 后端容器以镜像里的 `spring` 用户运行。微信支付两个 PEM 要让这个用户能读：`docker compose … run --rm --no-deps --entrypoint id backend -u` 查到 uid 后 `chown <uid> /etc/low-altitude/secrets/wechat/*.pem && chmod 400 …`。
- `INSPECTION_DATA_ENCRYPTION_BASE64_KEY` 加密了联系人、地址等敏感资料，**丢了就读不出来**。把它单独离线保存一份（不和数据库备份放在一起）。
- 防火墙只开 22、80、443。MinIO 控制台只绑本机，用 `ssh -L 9001:127.0.0.1:9001 <服务器>` 再打开 `http://127.0.0.1:9001`。
- 第一次启动时建首个平台运营账号，做法见下面 §3.1。
- 文件存储默认走 compose 里的 MinIO（`PLATFORM_STORAGE_PROVIDER=s3`），配置项和换成云对象存储的做法见 §3.2。

App 构建：公开构建的接口地址在构建时给，例如
`VITE_INSPECTION_API_BASE_URL=https://api.<你的域名> npm run -s verify:public-production-preview`（`apps/mobile/.env.production` 里是占位 `https://api.example.com`；不要用 `.env.production.local`，检查脚本会拒绝）。哪些功能随首发打开见 `docs/ops/发布开关.md`。

### 3.1 首个平台运营账号（一次性引导）

生产库里没有任何账号，运营端登录不了。后端带了一个一次性的引导：设了 `PLATFORM_BOOTSTRAP_OPERATOR_LOGIN` 时，启动时经身份模块建一个平台运营账号（挂在平台机构下，授 `PLATFORM_OPERATOR` 全局角色；没有平台机构时先建一个，编码 `PLATFORM`），之后其他账号和机构都在运营端建。

| 变量 | 说明 |
| --- | --- |
| `PLATFORM_BOOTSTRAP_OPERATOR_LOGIN` | 登录名：小写字母开头，4–32 位小写字母、数字、`_`、`-`。不设就什么都不做 |
| `PLATFORM_BOOTSTRAP_OPERATOR_PASSWORD_FILE` | 口令文件的路径（推荐）：文件里只有口令一行，只让运行后端的用户读（400） |
| `PLATFORM_BOOTSTRAP_OPERATOR_PASSWORD` | 或者直接给口令（两者只能给一个） |
| `PLATFORM_BOOTSTRAP_OPERATOR_DISPLAY_NAME` | 显示名，默认“平台运营”，最多 40 字 |

口令要求：12–64 个英文字母、数字或英文符号（不含空格和中文），大写字母、小写字母、数字、符号四类里至少三类，不能包含登录名。不合要求时后端不启动，日志只说哪条不合要求，**不打印口令**。账号已存在（不管是不是这次建的）时什么都不改（不改口令、不加角色），只记一行日志；所以重启不会覆盖口令。

步骤：

```sh
# 1. 口令文件（口令用密码管理器生成，不发聊天、不进工单）
sudo chmod 700 /etc/low-altitude/secrets/bootstrap
sudo sh -c 'umask 077; cat > /etc/low-altitude/secrets/bootstrap/operator-password'   # 粘贴口令，回车，Ctrl-D
UID_SPRING=$(sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml run --rm --no-deps --entrypoint id backend -u)
sudo chown "$UID_SPRING" /etc/low-altitude/secrets/bootstrap/operator-password && sudo chmod 400 /etc/low-altitude/secrets/bootstrap/operator-password

# 2. 在 prod.env 里加两行（容器里的路径同宿主机，compose 已把 secrets/bootstrap 只读挂进去）
#    PLATFORM_BOOTSTRAP_OPERATOR_LOGIN=<登录名>
#    PLATFORM_BOOTSTRAP_OPERATOR_PASSWORD_FILE=/etc/low-altitude/secrets/bootstrap/operator-password
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml up -d backend
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml logs backend | grep "platform operator bootstrap"
#    看到 “created platform operator account <登录名>” 就是建好了

# 3. 用完马上删掉：prod.env 里那两行、口令文件，然后再 up -d backend 一次
sudo sed -i '/^PLATFORM_BOOTSTRAP_OPERATOR_/d' /etc/low-altitude/prod.env
sudo shred -u /etc/low-altitude/secrets/bootstrap/operator-password
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml up -d backend
```

4. 用这个账号登录运营端，确认能进；口令交给负责运营的人后请他尽快在密码管理器里保管。以后再要平台运营账号，同样用这个引导换一个登录名；平台客服（`PLATFORM_SUPPORT`）引导不建，做法待定（`docs/delivery/配置与权限说明.md` §1.3）。

### 3.2 文件存储（对象存储）

六类文件（运营端素材、商品图片、批量导入文件、机构资质附件、服务订单交付文件、售后凭证）走平台文件存储；巡检预约附件和交付文件仍走巡检自己的 `INSPECTION_MINIO_*`。compose 已经把它们接到同一个 MinIO：

| 变量 | compose 里的值 | 说明 |
| --- | --- | --- |
| `PLATFORM_STORAGE_PROVIDER` | `s3`（可在 prod.env 覆盖） | `local` 时这六类在生产上传下载都回 503 |
| `PLATFORM_STORAGE_S3_ENDPOINT` | `http://minio:9000` | 后端访问存储的内部地址 |
| `PLATFORM_STORAGE_S3_ACCESS_KEY`、`_SECRET_KEY` | `LA_MINIO_ACCESS_KEY`、`LA_MINIO_SECRET_KEY` | 只放 prod.env |
| `PLATFORM_STORAGE_S3_PRIVATE_BUCKET` | `<环境名>-platform-private` | 私有桶（匿名不可读），`minio-init` 建 |
| `PLATFORM_STORAGE_S3_PUBLIC_BUCKET` | `<环境名>-public-assets` | 公开桶（匿名只读） |
| `PLATFORM_STORAGE_S3_PUBLIC_BASE_URL` | `https://<LA_FILES_DOMAIN>/<环境名>-public-assets` | 公开文件对外地址前缀，必须 https |

对象键是“模块名/模块生成的键”（如 `mall/products/<uuid>.jpg`、`identity/organizations/<机构>/qualification/<附件>`），模块之间不互读。私有文件只经后端受权接口读回，不给存储地址。后端启动时自检这几项，缺一项或格式不对就不启动，日志列出全部缺项和变量名，不打印密钥。

换成云厂商的对象存储（S3 兼容接口）：改 `PLATFORM_STORAGE_S3_ENDPOINT`（只写到域名）、`_REGION`、账号密钥、两个桶名和 `_PUBLIC_BASE_URL`（一般是 CDN 域名）；厂商只支持“桶名在域名里”的寻址时设 `PLATFORM_STORAGE_S3_PATH_STYLE=false`。公开桶要设成匿名只读，私有桶不能公开。

## 4. 健康检查与监控

- 后端：Spring Boot Actuator 的 `/actuator/health`（已有，`show-details: never`，只回 `{"status":"UP"}`；不加新依赖）。镜像的 `HEALTHCHECK` 和 compose 的 `healthcheck` 都打它；对外只经 nginx 的 `https://<API 域名>/healthz` 暴露这一个，其余 `/actuator/*` 在 nginx 上回 404。
- 数据库、Redis、MinIO、nginx 各有 compose 健康检查；`backend` 等前三个健康后才启动，`nginx` 等后端健康后才启动。
- `infra/prod/check-health.sh`：容器状态 + 从外面走一遍三个域名 + 证书剩余天数，不对时退出码 1。建议 cron 每 5 分钟跑一次，非 0 时发告警（短信、企业微信机器人等，接哪个你定）：

  ```cron
  */5 * * * * root /opt/low-altitude/infra/prod/check-health.sh > /var/log/low-altitude/health.log 2>&1 || <你的告警命令>
  ```

- 还没有的：指标采集（Prometheus 一类）、日志集中检索、错误告警。上量前再加，加的时候按 AGENTS.md §14 说明依赖。每天要有人看：对账结果（`GET /api/v1/platform/trade/reconciliation`）、备份日志、磁盘空间。

## 5. 数据库备份

`infra/prod/backup/pg-backup.sh`：用 postgres 容器里的 `pg_dump -Fc` 导出到宿主机 `${LA_BACKUP_DIR}/db/<库名>-<时间>.dump`，写 `.sha256`，导完马上 `pg_restore -l` 校验能读；保留 `LA_BACKUP_KEEP_DAYS` 天（默认 14）；设了 `LA_BACKUP_OFFSITE_CMD` 时再拷到异地。只读数据库，不停服务。

```cron
15 3 * * * root /opt/low-altitude/infra/prod/backup/pg-backup.sh >> /var/log/low-altitude/backup.log 2>&1
```

对象存储（附件、交付文件、展示图，`<环境名>-inspection-private`、`<环境名>-platform-private`、`<环境名>-public-assets` 三个桶）另外备份：`mc mirror` 把 MinIO 的桶同步到异地对象存储，每天一次；或者直接用云厂商的对象存储代替 MinIO（改 `INSPECTION_MINIO_*` 和 `PLATFORM_STORAGE_S3_*` 指过去，见 §3.2）。Redis 不备份（只是缓存和去重）。

**每月演练一次恢复**（不动正式库）：

```sh
sudo infra/prod/backup/pg-restore.sh <备份文件名> --check
```

## 6. 恢复

| 情况 | 做法 |
| --- | --- |
| 要找回几条被误改的数据 | `pg-restore.sh <备份> --into restore_YYYYMMDD` 恢复到新库，查出来手工补回；用完 `DROP DATABASE` |
| 正式库坏了、或发布后数据被迁移改坏 | `pg-restore.sh <备份> --replace-production`：要输入库名确认；停后端 → 现库改名为 `<库名>_before_<时间>` 留底 → 新建库恢复 → 起后端（启动时迁移补到当前版本）。核对无误后再删留底的库 |

恢复会丢掉备份之后的数据。涉及钱的：恢复后马上对恢复点之后的日子重跑对账（`POST /api/v1/platform/trade/reconciliation/runs?date=…&redo=true`），以微信的账单为准逐笔核对，必要时人工补单。

## 7. 发布

一次发布只做一件事：后端、H5、App 分开发，出了问题容易判断回滚哪个。

**后端**

```sh
cd /opt/low-altitude && git fetch && git checkout <发布的提交>
sudo infra/prod/backup/pg-backup.sh                       # 发布前先备份（迁移只能往前）
TAG=$(git rev-parse --short HEAD)
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml build backend
sudo sed -i "s/^LA_BACKEND_TAG=.*/LA_BACKEND_TAG=$TAG/" /etc/low-altitude/prod.env
sudo docker compose --env-file /etc/low-altitude/prod.env -f infra/prod/docker-compose.yml up -d backend
sudo infra/prod/check-health.sh
```

把每次发布的提交号、时间、备份文件名记下来（发布记录），回滚要用。旧镜像至少留最近 3 个（`docker image ls low-altitude/backend`）。

**H5**

```sh
# 在构建机上：cd apps/mobile && VITE_INSPECTION_API_BASE_URL=https://api.<域名> npm run -s verify:public-production-preview
# 把 apps/mobile/dist/build/h5 整个传到服务器的 /srv/low-altitude/web/releases/<版本>/
cd /srv/low-altitude/web
sudo ln -sfn releases/<版本> current.new && sudo mv -T current.new current   # 原子切换
```

`index.html` 不缓存、`/assets/` 带哈希长缓存，切链接后新打开的页面就是新版本。旧版本目录留最近 5 个。

**App（Android / iOS）**：按 AGENTS.md §15 的 L4 做真机验收后再上架；App 版本和后端接口要兼容（后端先发、App 后发；接口只加不删）。

## 8. 回滚

| 回滚什么 | 怎么做 | 注意 |
| --- | --- | --- |
| 后端 | 把 `prod.env` 的 `LA_BACKEND_TAG` 改回上一个提交号，`up -d backend`，跑 `check-health.sh` | 迁移只能往前。Flyway 默认忽略库里比代码新的迁移，旧版本能启动；按规矩新迁移只加不改（加表、加可空列），旧代码照常工作。新迁移改了旧代码依赖的结构时，只回滚代码不够，要按 §6 用发布前的备份恢复，并接受丢失发布后的数据 |
| H5 | `ln -sfn releases/<上一个版本> current.new && mv -T current.new current` | 立即生效 |
| nginx 配置 | `git checkout <上一个提交> -- infra/prod/nginx`，`docker compose … exec nginx nginx -s reload`（模板改了要 `up -d --force-recreate nginx`） | 改之前先 `docker compose … exec nginx nginx -t` |
| 环境变量 | `prod.env` 改动前先 `cp prod.env prod.env.<日期>`，回滚时拷回来再 `up -d` | 不要把这些副本放到别的机器上 |
| 发布开关 | 改回 `release-features.json` 重新构建 H5 / App | App 已经发出去的只能发新版本 |

## 9. 日志

- 所有容器日志写标准输出，docker 的 `json-file` 驱动按大小轮转：每个容器最多 5 个 20 MB（`docker-compose.yml` 的 `x-logging`）。看日志：`docker compose … logs -f --since 1h backend`。
- 脚本日志在 `/var/log/low-altitude/`，`/etc/logrotate.d/low-altitude` 每天轮转、留 30 天。
- 日志里不该有令牌、密钥、手机号、精确坐标（AGENTS.md §14）；微信支付自检和启动检查的报错只写配置项名字。排查时也不要把 `prod.env` 内容贴到聊天或工单里。
