# 微信支付联调清单（S2-1）

> 建立：2026-11-22（计划 `docs/redesign/08-后续开发计划.md` S2-1）。
> 用途：拿到真实的服务商号、证书和二级商户号以后，照这份清单准备材料、放到服务器、跑自检、逐项联调并填验收表。
> 现状：交易模块只和本机模拟微信（`infra/dev/fake-wechat/server.mjs`）通过信，**和真实微信一次都没有联调过**。
> 关联：用例细节和要在联调时确认的已知疑点见 `docs/redesign/05-微信支付联调记录.md`（本清单不重复那里的 17 个用例说明，只给步骤和验收表）；部署方式见 `docs/ops/部署与回滚.md`。

## 1. 要你准备的材料

全部是真实值，**只放服务器，不发到聊天、邮件、截图，不进仓库**。如果在这些地方出现过，联调后到商户平台重新生成。

| # | 材料 | 从哪拿 | 放在哪（服务器） | 对应配置 |
| --- | --- | --- | --- | --- |
| 1 | 服务商户号（10 位数字），已开通“平台收付通” | 微信支付服务商平台 | 环境变量文件 | `TRADE_WECHAT_SP_MCHID` |
| 2 | 移动应用 APPID（wx 开头），已和服务商号绑定 | 微信开放平台 → 移动应用 | 环境变量文件；App 的 `manifest.json` 微信支付模块（iOS 还要 Universal Links） | `TRADE_WECHAT_SP_APPID` |
| 3 | 服务商 API 证书私钥 `apiclient_key.pem`（PKCS#8，`-----BEGIN PRIVATE KEY-----`） | 商户平台 → 账户中心 → API 安全 → 申请 API 证书 | `/etc/low-altitude/secrets/wechat/apiclient_key.pem`，属主是运行后端的用户，权限 `400` | `TRADE_WECHAT_MERCHANT_PRIVATE_KEY_PATH` |
| 4 | API 证书序列号（40 位十六进制） | 同上，证书详情；或 `openssl x509 -in apiclient_cert.pem -noout -serial` | 环境变量文件 | `TRADE_WECHAT_MERCHANT_SERIAL_NO` |
| 5 | APIv3 密钥（32 个字符） | 商户平台 → API 安全 → 设置 APIv3 密钥 | 环境变量文件（文件权限 `600`） | `TRADE_WECHAT_API_V3_KEY` |
| 6 | 微信支付公钥 `pub_key.pem` 和公钥 ID（`PUB_KEY_ID_` 开头） | 商户平台 → API 安全 → 微信支付公钥（还在用平台证书的账户要先申请公钥） | `/etc/low-altitude/secrets/wechat/pub_key.pem`，权限 `400` | `TRADE_WECHAT_PLATFORM_PUBLIC_KEY_PATH`、`TRADE_WECHAT_PLATFORM_PUBLIC_KEY_ID` |
| 7 | 外网 HTTPS 回调地址：`https://<API 域名>/api/v1/trade/channels/wechat/notifications` | 生产域名定了以后（见部署说明） | 环境变量文件；Nginx 已把 `/api/` 转给后端 | `TRADE_WECHAT_PAYMENT_NOTIFY_URL`、`TRADE_WECHAT_REFUND_NOTIFY_URL` |
| 8 | 1–2 家先开通的商家：进件通过的二级商户号 | 服务商平台 → 收付通 → 二级商户进件 | 数据库 `trade_merchant_account`（用平台运营接口登记，见 §3 第 3 步） | — |
| 9 | 一个平台运营账号（`PLATFORM_OPERATOR` 角色） | 现在没有页面，开发种子里有意不建；S3 运营端做好之前由我们用一次性 SQL 授权（见 §3 第 2 步） | 身份库 | — |
| 10 | 一个 0.01 元的测试供给（联调用，联调后下架） | 运营在商品与供给里建，或临时改价 | 商城库 | — |

注意：

- 不要把 `apiclient_cert.pem`（证书）当私钥，也不要用 PKCS#1 格式（`-----BEGIN RSA PRIVATE KEY-----`）。自检会分别报出来。
- 不要把 `pub_key.pem` 放成自己证书的公钥。自检会比对两把密钥是不是同一对。
- 环境变量文件和两个 PEM 只让运行后端的用户读。生产 compose 把 `/etc/low-altitude/secrets/wechat/` 只读挂进容器（见 `infra/prod/docker-compose.yml`）。

## 2. 放在哪

```text
/etc/low-altitude/
├── prod.env                       # infra/prod/.env.example 填好后的文件，权限 600（含 APIv3 密钥）
└── secrets/
    └── wechat/
        ├── apiclient_key.pem      # 400
        └── pub_key.pem            # 400
```

`prod.env` 里与微信支付有关的几行（值留空的地方由你填）。生产 compose 把这个目录按同一路径只读挂进后端容器，所以路径在宿主机和容器里一样，自检脚本可以直接读：

```sh
TRADE_WECHAT_ENABLED=true
TRADE_WECHAT_SP_MCHID=
TRADE_WECHAT_SP_APPID=
TRADE_WECHAT_MERCHANT_SERIAL_NO=
TRADE_WECHAT_MERCHANT_PRIVATE_KEY_PATH=/etc/low-altitude/secrets/wechat/apiclient_key.pem
TRADE_WECHAT_API_V3_KEY=
TRADE_WECHAT_PLATFORM_PUBLIC_KEY_ID=
TRADE_WECHAT_PLATFORM_PUBLIC_KEY_PATH=/etc/low-altitude/secrets/wechat/pub_key.pem
TRADE_WECHAT_PAYMENT_NOTIFY_URL=https://<API 域名>/api/v1/trade/channels/wechat/notifications
TRADE_WECHAT_REFUND_NOTIFY_URL=https://<API 域名>/api/v1/trade/channels/wechat/notifications
```

## 3. 联调步骤

### 第 1 步 本机自检（不连后端）

在服务器上（要 Node 18 以上；没有时把脚本和文件拷到一台装了 Node、同样受控的运维机上跑，跑完删掉副本）：

```sh
WECHAT_PREFLIGHT_ENV_FILE=/etc/low-altitude/prod.env node infra/scripts/wechat-pay-preflight.cjs --offline
```

逐项输出“通过 / 注意 / 不通过 / 跳过”，只说哪里不对、怎么改，不打印密钥和文件内容。有“不通过”就先改，改完再跑。

### 第 2 步 准备平台运营账号

S3 运营端之前没有页面。用数据库给一个已存在的账号加平台运营角色（账号本身由身份模块建；**不要用开发种子账号**，生产库里也不该有）：

```sql
-- 在生产库执行前先确认 login_name；只加角色，不改密码。
INSERT INTO identity_user_role (user_id, role_id, organization_id)
SELECT u.id, r.id, NULL
FROM identity_user u JOIN identity_role r ON r.role_code = 'PLATFORM_OPERATOR'
WHERE u.login_name = '<平台运营账号>'
ON CONFLICT DO NOTHING;
```

### 第 3 步 启动后端、登记子商户号

1. 后端启动时会跑同一套配置自检（只在真实微信模式下）：有一项不通过就不启动，日志里一次列出全部不通过项和对应的配置名，不带密钥和路径；“注意”项只记 WARN 日志。
2. 登记商家的收款账户（每家一次）：

   ```sh
   curl -X PUT https://<API 域名>/api/v1/platform/trade/merchant-accounts/<机构 ID> \
     -H "Authorization: Bearer <平台运营令牌>" -H 'Content-Type: application/json' \
     -d '{"subMchid":"<二级商户号>","active":true}'
   ```

### 第 4 步 后端自检（向微信发只读请求）

```sh
WECHAT_PREFLIGHT_ENV_FILE=/etc/low-altitude/prod.env \
PREFLIGHT_BASE_URL=https://<API 域名> \
PREFLIGHT_LOGIN_NAME=<平台运营账号> \
PREFLIGHT_PASSWORD_FILE=/root/.preflight-password \
PREFLIGHT_SUB_MCHID=<第 3 步登记的二级商户号> \
node infra/scripts/wechat-pay-preflight.cjs
```

后端接口是 `POST /api/v1/platform/trade/channel-checks?subMchid=…`（契约 `contracts/openapi-trade.yaml` 0.4.0 `checkPaymentChannel`，只给平台运营）。它先列后端实际加载的配置自检结果，再：

- 按一个 `CHK` 开头的、不存在的商户订单号查单 → 期望 `QUERY_PAYMENT 通过`（微信验过签地回答 ORDER_NOT_EXIST）；
- 按一个不存在的退款单号查退款 → 期望 `QUERY_REFUND 通过`（RESOURCE_NOT_EXISTS）。

不下单、不关单、不退款、不写数据库，可以随时重复跑。常见结果：

| 结果 | 说明 | 怎么办 |
| --- | --- | --- |
| `SIGN_ERROR`（401） | 请求签名不对 | 证书序列号和私钥不是同一张证书；重新核对 #3、#4 |
| 验签不过（UNTRUSTED） | 应答签名对不上 | 微信支付公钥或公钥 ID 不属于这个服务商号；核对 #6 |
| `NO_AUTH` / `INVALID_REQUEST` | 没权限 | 子商户号没和服务商号绑定，或没开通收付通 |
| 连不上（NETWORK） | 网络 | 服务器出口、DNS、防火墙要能访问 `api.mch.weixin.qq.com:443` |
| `UNVERIFIED_ERROR`（404） | 微信回了“单不存在”但没带签名 | 签名和网络其实是通的；这是联调记录 §3 第 12 条要确认的事，记下来，代码判法要改（否则过期单关不掉） |

关于“下载平台证书”：本项目只接“微信支付公钥”模式，不下载平台证书（联调记录 §3 第 5 条）。账户如果只有平台证书，先在商户平台申请微信支付公钥。

### 第 5 步 按用例联调

用 0.01 元的测试供给，顺序做（每个用例的具体预期见 `docs/redesign/05-微信支付联调记录.md` §2 的编号）：

1. **下单**（用例 1、2）：App 确认订单 → 提交 → 收银台 → 确认支付，拿到 prepay_id。
2. **调起与付款**（用例 3、6）：真机微信收银台，收款方是商家，金额 0.01 元；再试一次取消付款。
3. **回调**（用例 4、5）：付款后订单变“已付款”；查 `trade_channel_notification` 有一条 APPLIED；记下回调时间戳和服务器时间差。
4. **查单**（用例 7、8）：临时让回调不可达再付一单，App 点“刷新结果”；另下一单不付，等 30 分钟看是否关单。
5. **退款**（用例 10、11、12）：付款后发货前取消（全额退）；0.02 元订单分两次部分退（商家接口，`node infra/scripts/dev-merchant-order.cjs` 的写法照搬到生产时换成真实商家操作员账号）。
6. **对账**（用例 14、15、16）：第二天 10 点后 `POST /api/v1/platform/trade/reconciliation/runs?date=<昨天>`，再 `GET /api/v1/platform/trade/reconciliation?date=<昨天>&format=CSV`，前面的单应全部匹配。

联调完：测试供给下架，0.01 元订单都已退款或关闭；联调中出现过密钥的，到商户平台重新生成并更新服务器文件后，再跑一次第 4 步。
