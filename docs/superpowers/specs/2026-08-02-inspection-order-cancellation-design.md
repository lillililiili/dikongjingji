# 巡检订单取消设计

## 目标

允许客户在巡检方案确认完成前主动取消订单。该阶段尚未发生支付，因此产品与代码统一使用“取消订单”，不展示“退款”“退款成功”或资金原路退回等文案。

取消必须形成完整状态闭环：前端给出明确入口和二次确认，后端校验订单归属与当前状态，数据库原子更新，订单中心能够继续查看“已取消”记录，已取消订单不得再发布或确认方案。

## 可取消状态

| 当前阶段 | 预约状态 | 是否可取消 | 取消结果 |
| --- | --- | --- | --- |
| 待方案 | `SUBMITTED` | 是 | 预约转为 `CANCELLED` |
| 待确认 | `PLAN_PUBLISHED` | 是 | 预约转为 `CANCELLED`，当前已发布方案转为 `WITHDRAWN` |
| 服务安排/执行中 | 已存在服务单 | 否 | 保持原状态，接口返回状态冲突 |
| 待验收/已完成 | 已存在服务单 | 否 | 保持原状态，接口返回状态冲突 |
| 已取消 | `CANCELLED` | 无需再次取消 | 重复请求幂等返回当前已取消记录 |

“方案确认完成”以服务单已经创建为最终判断条件。即使客户端页面状态过期，只要服务单已创建或方案已经确认，后端都必须拒绝取消，避免取消与确认方案并发时产生双重结果。

## 页面入口与交互

采用已确认的方案 A：

- “订单已提交”页在内容区底部、固定操作栏上方显示次要操作“取消订单”。
- “服务方案确认”页仅在方案尚未确认时，于内容区底部、固定确认区域上方显示同一规格的“取消订单”。
- “我的订单”列表卡片不增加取消按钮，避免卡片拥挤和误触。
- 方案确认完成、进入服务安排后不再显示取消入口。
- 已取消订单仍可从“我的订单”打开，页面显示“订单已取消”，主操作仅保留“返回订单”，不得继续进入或确认已撤回方案。

点击“取消订单”后使用二次确认弹窗：

- 标题：`确认取消订单？`
- 说明：`取消后服务将停止安排，本订单未付款，不涉及退款。`
- 次按钮：`暂不取消`
- 主按钮：`确认取消`

提交期间按钮显示“取消中…”并禁止重复点击。取消成功后刷新预约数据，展示“订单已取消”；取消失败时保留当前页面和用户已查看的数据。

## 接口契约

新增客户接口：

```text
POST /api/v1/inspection/reservations/{reservationId}/cancel
```

请求头沿用现有并发与幂等约定：

- `Authorization: Bearer ...`
- `Idempotency-Key: <UUID>`
- `If-Match: <当前预约版本>`

成功返回 `200` 和最新 `ReservationResponse`，响应 `ETag` 为取消后的版本。

错误语义：

- `401`：未登录或令牌无效。
- `403/404`：非订单本人访问；对越权资源沿用现有隐藏资源策略。
- `409 INS_RESERVATION_NOT_CANCELLABLE`：方案已确认、服务单已创建或订单已进入执行阶段。
- `412 INS_VERSION_CONFLICT`：客户端预约版本已过期；前端重新读取订单后按最新状态展示。

接口不接收退款账户、退款金额或支付单号，也不创建任何退款记录。

## 后端状态与并发

取消操作在单个事务内完成：

1. 校验当前主体为订单客户本人，并具备本人取消权限。
2. 读取并锁定预约记录，校验 `If-Match` 版本。
3. 若预约已为 `CANCELLED`，按相同幂等键返回当前记录。
4. 校验不存在服务单，且当前方案没有进入 `CONFIRMED`。
5. 若存在 `PUBLISHED` 方案，将其更新为 `WITHDRAWN` 并递增版本。
6. 将预约从 `SUBMITTED` 或 `PLAN_PUBLISHED` 更新为 `CANCELLED`，递增版本并记录操作人和时间。
7. 写入现有审计/事件机制，事件名使用 `INSPECTION_RESERVATION_CANCELLED`；不得记录精确位置、联系人或令牌。

取消 SQL 必须在条件中同时限制允许的原状态、版本以及不存在服务单。方案确认和取消并发时，只允许一个事务成功；失败一方返回明确的版本或状态冲突，不得依赖前端先后顺序。

已有时段容量查询会排除 `CANCELLED`，取消成功后该预约不再占用相应时段容量。保留预约及方案历史，不物理删除业务数据。

## 前端数据与错误恢复

- 预约 API 增加类型化 `cancelReservation` 方法，复用现有鉴权、错误映射和 UUID 生成方式。
- 两个页面共用同一取消用例或最小控制器，避免分别写出不同状态判断和提示文案。
- 可取消判断只用于控制界面；后端始终是最终事实源。
- 收到 `INS_VERSION_CONFLICT` 或 `INS_RESERVATION_NOT_CANCELLABLE` 后重新读取预约：若已进入服务安排，隐藏取消入口并引导查看服务安排；若已被取消，直接展示已取消状态。
- 网络失败时提示“取消失败，请检查网络后重试”，不改变本地订单状态。
- 取消成功后使订单中心列表及阶段数量失效，返回订单中心时重新拉取，确保“待方案/待确认”数量同步减少。

## 权限与审计

- 新增或复用最小权限 `inspection.reservation.cancel.own`，仅客户本人可调用。
- 平台或服务商如需代客取消，应另开任务定义权限、原因和审计流程，本次不顺带开放。
- 审计至少记录预约 ID、客户主体 ID、取消前状态、取消后状态、时间和请求 ID。
- 不记录地址明文、联系方式、访问令牌或完整请求体。

## 修改边界

预计涉及：

- 移动端预约 API、取消交互复用逻辑、订单已提交页、方案确认页及对应测试。
- 后端预约应用服务、存储接口/Mapper、预约控制器、异常映射及对应测试。
- OpenAPI 契约与示例；如现有权限种子不包含取消权限，补充最小权限种子。

明确不修改：

- 支付、退款、资金流水、优惠、发票或结算。
- 服务执行开始后的售后取消规则。
- 订单列表卡片布局、巡检目录、预约表单、天气、登录和其他一级页面。
- 已有用户未提交改动；不进行无关重构、格式化或依赖升级。

## 测试与验收

后端：

- 本人可取消 `SUBMITTED` 预约，状态变为 `CANCELLED`，版本递增。
- 本人可取消 `PLAN_PUBLISHED` 预约，预约变为 `CANCELLED`，当前方案变为 `WITHDRAWN`。
- 重复取消返回同一已取消结果，不产生重复事件。
- 非本人无法取消，越权请求不暴露订单信息。
- 已确认方案或已存在服务单时拒绝取消。
- 取消与确认方案并发时仅一个成功。
- 版本过期返回 `412`；无效状态返回 `409`。
- 取消后时段容量释放，服务商无法再次发布方案，客户无法确认已撤回方案。

移动端：

- 待方案页和待确认页显示“取消订单”，其他阶段不显示。
- 二次确认选择“暂不取消”时不发请求、不改变页面。
- 提交期间不可重复点击；成功后显示“订单已取消”。
- 网络失败、版本冲突和状态冲突均有正确恢复行为。
- 已取消订单不再进入方案确认页。
- 返回订单中心后列表与阶段数量刷新。

回归：

- 移动端相关单元测试、全量测试、类型检查和 H5 构建通过。
- 后端预约、方案、订单相关测试及模块 `clean test` 通过。
- OpenAPI 契约校验通过。
- HBuilderX Android 真机验证两个入口、二次确认、成功状态、返回订单中心和并发状态刷新；本阶段不云打包 APK。
