# 巡检时间选择设计

## 1. 目标

把预约页“期望时间”的系统日期选择器替换为参考图样式的底部弹层。用户确认日期和时段后，原位置显示“日期 + 时段”，预约提交使用后端真实余量校验。

视觉基线为用户提供的“选择服务时间”截图。只复刻其中的时间选择弹层，不新增截图背景中的“确认订单”页面。

## 2. 范围

本次包含：

- 现有 `/pages/service/inspection/booking` 页面中的时间选择交互。
- 固定日期范围内的真实可预约时段查询。
- 每个时段固定 9 个名额。
- 预约提交时的容量并发校验。
- 选择结果回填、错误恢复和对应测试。

本次不包含：

- 新页面或新路由。
- 排班管理后台、服务商自定义时段或动态容量配置。
- 支付、退款、确认订单和新的预约取消功能。
- M01、M02、服务详情、方案、履约及交付页面调整。

## 3. 去冗余结论

本设计不新增时段库存表。三个时段和容量 9 由后端固定规则提供；余量直接按现有预约记录实时聚合。

本设计不新增 Pinia store。弹层开关、临时选择和加载状态属于预约页面局部状态。

本设计不新增时间快照列。预约只持久化日期和稳定时段编码；当前固定时段编码与起止时间是一一对应的不可配置规则。

本设计不新增取消预约接口。余量统计排除现有 `CANCELLED` 状态，因此未来既有流程产生取消状态时会自然释放名额。

为了防止并发超额，创建预约时在同一事务内锁定对应服务记录，再统计目标日期和时段的有效预约数。当前规模下按服务串行提交足够简单可靠，不引入库存计数同步或额外锁表。

## 4. 页面交互

1. 用户点击预约页“期望时间”行。
2. 页面背景变暗，底部弹出圆角时间选择面板。
3. 面板默认展示今天起连续 4 天；标签依次使用“今天”“明天”或星期。
4. “更多日期”在当前弹层内打开已有组件库的日历能力，不再调用系统日期选择器。
5. 可选择日期范围为今天至未来 30 天，过去日期不可选。
6. 选择日期后查询该日期三个时段的真实余量：
   - `MORNING`：`09:00–12:00`
   - `AFTERNOON`：`14:00–17:00`
   - `EVENING`：`18:00–21:00`
7. 可选时段显示具体时间；余量为 0 时不可点击并显示“已约满”。
8. 选中状态使用橙色描边、浅橙背景和橙色文字。
9. 未选时段时确认按钮不可用。选中后，摘要显示“已选择：7月30日 09:00–12:00”。
10. 点击“确定”后关闭弹层，并在原“期望时间”位置显示相同的日期和时段。
11. 点击关闭按钮或遮罩时放弃本次临时选择，保留此前已经确认的值。
12. 再次打开弹层时恢复此前确认的日期和时段。

弹层由独立的 `InspectionTimePickerSheet` 组件负责。预约页面只负责打开弹层、接收确认结果和回填字段。

## 5. 前端数据模型

预约草稿使用一个可空的结构化字段，避免日期和时段出现只更新一半的状态：

```ts
interface BookingTimeSelection {
  serviceDate: string
  slotCode: 'MORNING' | 'AFTERNOON' | 'EVENING'
}
```

显示文案根据接口返回的日期、开始时间和结束时间生成，不把中文显示文案作为请求参数。

可预约时段 DTO 包含：

- `serviceDate`
- `slotCode`
- `startTime`
- `endTime`
- `remainingCount`
- `availability`：`AVAILABLE` 或 `FULL`

## 6. API

新增查询接口：

```text
GET /api/v1/inspection/services/{serviceId}/available-time-slots
    ?cityCode=370500
    &startDate=2026-07-31
    &days=4
```

`days` 最大为 31。接口按日期返回三个固定时段及真实余量。

现有预约创建请求把 `preferredServiceDate` 调整为：

```json
{
  "preferredServiceDate": "2026-07-31",
  "preferredTimeSlotCode": "MORNING"
}
```

预约响应返回相同字段。前端通过稳定编码和固定规则恢复显示时间。

## 7. 容量与并发

- 每个“服务 + 城市 + 日期 + 时段”容量固定为 9。
- 有效预约为状态不等于 `CANCELLED` 的预约。
- 可用量等于 `9 - 有效预约数`，最小为 0。
- 查询接口提供即时参考，预约创建接口才是最终容量事实源。
- 创建预约沿用现有 `Idempotency-Key`。同一幂等请求重复提交只创建一个预约、只占一个名额。
- 创建事务锁定服务记录后重新计数。计数小于 9 时插入预约；达到 9 时返回 `409 INS_TIME_SLOT_FULL`。
- 并发争抢最后一个名额时只有一个请求成功。

数据库只为 `inspection_reservation` 新增非空的 `preferred_time_slot_code`，并加入固定编码约束及查询索引。既有 `preferred_service_date` 保持不变。

## 8. 错误处理

- 首次加载和切换日期时显示轻量加载状态，未确认余量前禁止点击时段。
- 查询失败时在弹层内显示“时间加载失败”和重试按钮，不关闭弹层。
- 快速切换日期时取消或忽略旧请求，只允许最后一次响应更新界面。
- 已确认时段再次打开后若已经约满，清除临时选中状态并提示重新选择；原页面已确认值在用户重新确认前不变。
- 提交时返回 `INS_TIME_SLOT_FULL`，保留地点、项目、联系人、附件和说明，重新打开弹层并刷新余量。
- 过去日期、未知时段编码和超出查询范围由服务端返回参数错误。

## 9. 测试与视觉验收

前端测试：

- 打开、关闭和遮罩取消不误改已确认值。
- 日期、时段选中与原位置回填。
- 已约满时段禁用。
- 加载、失败、重试和旧请求竞态。
- 再次打开恢复已确认值。

后端测试：

- 固定三个时段和容量 9。
- 第 1 至第 9 个有效预约成功，第 10 个返回 `INS_TIME_SLOT_FULL`。
- 幂等重试不重复占用。
- 并发争抢最后名额只有一个成功。
- `CANCELLED` 预约不占容量。
- 城市、日期、时段编码和查询天数校验。

E2E：

```text
服务详情
→ 预约服务
→ 点击期望时间
→ 选择日期与时段
→ 确定
→ 原位置显示日期和时段
→ 提交预约
```

视觉验收在 375、390、430 CSS 逻辑像素宽度进行。每个宽度检查安全区、遮罩、弹层圆角、日期卡片、两列时段网格、禁用状态、摘要和确认按钮。按视觉规范保存至少两轮同视口截图对照与差异记录。

## 10. 预期修改边界

移动端只涉及：

- 预约页面。
- 新时间选择弹层组件。
- 预约领域模型和预约 API 客户端。
- 对应测试。

后端只涉及：

- 预约时段查询应用服务和读取接口。
- 预约创建校验。
- 预约持久化映射。
- 一条增量数据库迁移。
- OpenAPI、示例和对应测试。

不得顺便整理预约页面、升级依赖、修改公共组件或扩展其他交易流程。
