## S6-01 运营端新入驻的服务商没有“服务商资料”

- **现象**：演练场景 1、5 用运营端新建经营机构、审核资质、上架一项专业服务后：`GET /api/v1/pro-services/{id}` 里 `provider` 为 `null`（App 详情不显示服务商行，也就看不到“资质已审核”）；`GET /api/v1/providers/{org}` 404（服务商主页打不开）；机构操作员 `GET /api/v1/provider/profile` 403（工作台“服务商资料”不能提交，`城市开通模板.md` 第 6 步做不了）。按契约，需求发布页的可邀请服务商列表（`GET /api/v1/demand-providers`，“有服务商资料”）也不会列它。
- **复现**：`node infra/scripts/s6-rehearsal/01-resources.cjs`，第 25 步 `KNOWN`，实际 `{"provider":null,"providerPage":404,"workbenchProfile":403}`。
- **根因**：这几个接口都以 `inspection_provider_profile`（巡检迁移 V004 的“服务商资料”）为准，而这张表只有开发种子 `R__dev_inspection_provider_profiles.sql` 写；运营端没有建它的接口，批量导入里对应的 `06-inspection-provider-profiles.csv` 属于 `SERVICES`，`GET /api/v1/ops/imports/kinds` 显示 `writable=false`（只能预检）。运营端建专业服务时只校验“在用的服务商机构”，所以服务能上架，但服务商那一行出不来。
- **影响**：第二城市（或任何新入驻）的服务商上线后，专业服务详情没有服务商、没有主页、不能被需求“仅邀请”、不能在工作台维护服务商资料；巡检服务目录同理（详情的服务商卡片读同一张表）。
- **处理**：在运营端“机构与资质”加“开通服务商资料”（按 08 计划 §5 S4-4 的默认决定：资料由机构在工作台填、平台在运营端审核，这里只补“开通”这一步）。
  - 两张表的关系：`inspection_provider_profile`（巡检 V004）是“这家机构是服务商”的开关行（图标、资质说明、团队介绍、在用 / 停用），专业服务详情的服务商行、服务商主页、需求邀请、工作台“服务商资料”的权限都看它；`pro_provider_profile`（专业服务 V003，S4-4）是主页上显示的资料，机构在工作台提交、平台在“服务商资料审核”里审。后者的提交和审核原来就有，缺的只是前者的建立入口。
  - 契约 `contracts/openapi-ops-organization.yaml` 1.0.0 → **1.1.0**：新增 `POST /api/v1/ops/organizations/{organizationId}/provider-profile`（平台运营，没有请求体，幂等：已开通直接返回、不记操作记录；停用的恢复在用）；机构详情加 `providerProfileStatus`（NOT_OPENED / ACTIVE / DISABLED，企业客户为 null）；操作记录加 `PROVIDER_PROFILE_OPEN`；错误码加 409 `OPS_QUALIFICATION_NOT_APPROVED`（资质要先审核通过，看机构的 `qualification_reviewed_at`）、422 `OPS_PROVIDER_PROFILE_NOT_APPLICABLE`（企业客户或停用机构）。
  - 后端：身份模块 `OrganizationOnboardingService.openProviderProfile` 锁住机构行、检查类型和资质后，经新端口 `OnboardingPorts.ProviderProfiles` 调巡检模块的 `InspectionProviderProfiles.open`（只写 `inspection_provider_profile` 一张表：建一行在用、图标 `PROVIDER_INITIAL`、资质说明和团队介绍留空），端口在启动模块 `OnboardingPortsConfiguration` 接，模块之间不互读表。身份迁移 **V011**（`V011__identity_provider_profile_open_operation.sql`）只放宽操作记录动作的 CHECK 约束。
  - 管理端：机构详情加“服务商资料”页签（经营机构才有）：状态、资质是否通过、“开通服务商资料”按钮（资质没通过时不可点并说明原因）、已开通后跳“服务商资料审核”。错误码有中文说明。
  - 批量导入 `06-inspection-provider-profiles.csv` **仍只能预检**：它属于“巡检和专业服务”这一类（06–06i 一起导，整类 `writable=false`），单独让 06 可写要拆导入类别、改导入契约和校验；而且 06 表的 logo、资质说明、团队介绍三列在“开通”里没有对应的写入（开通只建开关行），不是直接复用同一个应用服务就能做的。新城市的服务商在“机构与资质”里逐家开通（`城市开通模板.md` 第 6 步、`运营操作手册.md` §2.2 第 8 步）。
  - 演练脚本：`01-resources.cjs`、`05-city.cjs` 去掉两处 `INSERT INTO inspection_provider_profile`，改成经 `fixtures.cjs` 的 `openProviderProfile()` 调新接口；01 新增几步：资质审核前开通 409、未开通时服务详情 `provider=null`、开通且重复调用幂等（操作记录只有一条）、需求可邀请服务商列表含它、工作台提交主页资料 → 运营审核通过 → App 主页显示。原来“资质未审核时服务商不显示‘资质已审核’”那一步去掉了（开通要求资质先通过，同样的断言由后面“资料改动后回到待审核”一步覆盖）。
- **验证**：**主工作区复验（后端 `c98db9fa`，身份迁移 V011 已执行）**：`01-resources.cjs` 48/48 ALL OK、S6-01 一步 `FIXED`；`05-city.cjs` 38/38 ALL OK。分支上 `cd backend && mvn -o -q test` 全绿（新增 `InspectionProviderProfilesTest`、`OnboardingProviderProfilesPortTest`，`OrganizationOnboardingServiceTest`、`OpsOrganizationControllerTest`、`OpsOrganizationOpenApiContractTest`、`OrganizationOnboardingMapperSqlTest` 加了用例）；`cd apps/admin && npm test && npm run build` 通过（新增 `provider-profile-open.test.ts` 10 条）。**待主工作区**用新提交打包后端，跑 `node infra/scripts/s6-rehearsal/01-resources.cjs`：S6-01 那一步应打印 `FIXED`、不再有 `KNOWN`；`05-city.cjs` 的“淄博商家入驻”一步带出服务商资料 ACTIVE。

## S6-03 交易冒烟脚本的清理留下孤儿数据

- **现象**：场景 6 全库只读核对发现 20 条 `inspection_payment_attempt` 指向已不存在的交易订单（2026-11-23 10:24–16:26 建的）；另外库里有 215 条“交易物流”站内信（`TRADE_ORDER_SHIPPED / READY_FOR_PICKUP / REFUND_SUCCEEDED`）指向已删除的交易订单。
- **根因**：`infra/scripts/trade-smoke/lib.cjs` 的 `cleanupBuyer()` 删 dev-customer 的交易订单、支付、退款，但不删这些订单的站内信；`inspection.cjs` 按设计保留巡检预约和付款节点，却又用 `cleanupBuyer()` 删掉了它们的交易订单，留下指向空订单的付款记录。
- **影响**：只影响开发库的数据整洁和“全库一致性核对”的读数，不影响产品。演练脚本自己用闭包清理，不留这类数据（场景 6 的核对限定在演练数据上是 0 违反）。
- **处理**：已修（只改测试脚本）。`infra/scripts/trade-smoke/lib.cjs` 的 `cleanupBuyer()` 在删交易订单的同一个事务里先删：跳转目标是这些订单的站内信（`notification_message`，`target_type = 'TRADE_ORDER'`、`target_id` 是订单 ID、收件人是 dev-customer）和推送模拟记录（`notification_push_fake_delivery`，同样按目标），以及指向这些订单的巡检付款尝试（`inspection_payment_attempt.trade_order_id`，没有外键）。
  - 为什么选“连带清掉付款尝试”而不是“不删巡检的交易订单”：`fulfilment`、`payment`、`order`、`reconciliation` 几个冒烟各自也按 dev-customer 删全部交易订单，不删巡检的那几张，下一个冒烟照样会删掉、照样留孤儿；而且对账冒烟按天核对金额，多留几张巡检订单会干扰它。巡检的预约、服务单、付款节点仍按设计保留（S6-05），已付的节点仍读成已付；节点上记的首付退款单 ID 会指向已删的退款单（没有外键，只读页面不显示退款进度），记在脚本注释里。
  - 收费报名的“报名已退款”站内信跳转目标是报名单（`ACTIVITY_ORDER`），不是交易订单，不在这次范围。
  - 库里已有的 215 + 20 条孤儿这次没动（脚本只清自己跑出来的）；要清的话在开发库执行一次同样的条件即可。
- **验证（主工作区）**：跑任一交易冒烟（例如 `fulfilment.cjs` 之后再跑 `inspection.cjs`），结束后 `SELECT count(*) FROM notification_message m WHERE m.target_type='TRADE_ORDER' AND NOT EXISTS (SELECT 1 FROM trade_order t WHERE t.id=m.target_id)` 和 `SELECT count(*) FROM inspection_payment_attempt b WHERE NOT EXISTS (SELECT 1 FROM trade_order t WHERE t.id=b.trade_order_id)` 都不比跑之前多。**主工作区复验**：第一轮 14 个冒烟后站内信孤儿 215→230——`order`、`payment`、`fulfilment`、`reconciliation` 四个脚本自己直接删 dev-customer 的订单、不经 `cleanupBuyer()`，已在这四处同样先删通知和推送模拟记录；再跑这四个加 `aftersale` 后 230→230。随后在开发库一次性删掉已有孤儿（站内信 230 条、巡检付款尝试 20 条），现为 0。
