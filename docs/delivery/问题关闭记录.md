## S6-01 运营端新入驻的服务商没有“服务商资料”

- **现象**：演练场景 1、5 用运营端新建经营机构、审核资质、上架一项专业服务后：`GET /api/v1/pro-services/{id}` 里 `provider` 为 `null`（App 详情不显示服务商行，也就看不到“资质已审核”）；`GET /api/v1/providers/{org}` 404（服务商主页打不开）；机构操作员 `GET /api/v1/provider/profile` 403（工作台“服务商资料”不能提交，`城市开通模板.md` 第 6 步做不了）。按契约，需求发布页的可邀请服务商列表（`GET /api/v1/demand-providers`，“有服务商资料”）也不会列它。
- **复现**：`node infra/scripts/s6-rehearsal/01-resources.cjs`，第 25 步 `KNOWN`，实际 `{"provider":null,"providerPage":404,"workbenchProfile":403}`。
- **根因**：这几个接口都以 `inspection_provider_profile`（巡检迁移 V004 的“服务商资料”）为准，而这张表只有开发种子 `R__dev_inspection_provider_profiles.sql` 写；运营端没有建它的接口，批量导入里对应的 `06-inspection-provider-profiles.csv` 属于 `SERVICES`，`GET /api/v1/ops/imports/kinds` 显示 `writable=false`（只能预检）。运营端建专业服务时只校验“在用的服务商机构”，所以服务能上架，但服务商那一行出不来。
- **影响**：第二城市（或任何新入驻）的服务商上线后，专业服务详情没有服务商、没有主页、不能被需求“仅邀请”、不能在工作台维护服务商资料；巡检服务目录同理（详情的服务商卡片读同一张表）。
- **处理**：待办。正确修法要么在运营端“机构与资质”加“开通服务商资料”（身份 → 巡检跨模块端口 + 运营端契约 + 管理端页面），要么让导入的 06 表可写入；都要改契约，超出预算。演练里按 06 表的结果用 SQL 补一行后继续（脚本里有注释）。
- **验证（修好后）**：01 脚本第 25 步会从 `KNOWN` 变成 `FIXED`，同时去掉两处 `INSERT INTO inspection_provider_profile` 的绕过。

## S6-02 运营端不能打开活动的“允许候补”“允许团队报名”

- **现象**：场景 4 运营端新建的收费活动，场次满员后排候补 409 `ACT_WAITLIST_NOT_AVAILABLE`；运营端活动详情里没有候补、团队报名的字段；库里 `activity.waitlist_allowed = false`。
- **复现**：`node infra/scripts/s6-rehearsal/04-activity.cjs`，第 7 步 `KNOWN`，实际 `{"opsFields":[],"waitlistAllowed":"f"}`。
- **根因**：`contracts/openapi-ops-activity.yaml` 1.0.0 写明“候补和团队报名开关（候补、团队报名做好后再开放）不在这一版”；S5-3 候补、团队报名（活动契约 1.4.0、迁移 V006）已经合入，运营端没有跟着补开关，`waitlist_allowed`、`team_enrollment_allowed` 只在开发种子里为 true。
- **影响**：真实上线的活动用不了候补和团队报名（App 上满员就是满员）。
- **处理**：待办（要改运营端契约、后端、管理端表单）。演练里用 SQL 把演练活动的 `waitlist_allowed` 设为 true 后继续，候补转正付款整条链路通过。
- **验证（修好后）**：04 脚本第 7 步变 `FIXED`，去掉 `UPDATE activity SET waitlist_allowed` 的绕过。

## S6-03 交易冒烟脚本的清理留下孤儿数据

- **现象**：场景 6 全库只读核对发现 20 条 `inspection_payment_attempt` 指向已不存在的交易订单（2026-11-23 10:24–16:26 建的）；另外库里有 215 条“交易物流”站内信（`TRADE_ORDER_SHIPPED / READY_FOR_PICKUP / REFUND_SUCCEEDED`）指向已删除的交易订单。
- **根因**：`infra/scripts/trade-smoke/lib.cjs` 的 `cleanupBuyer()` 删 dev-customer 的交易订单、支付、退款，但不删这些订单的站内信；`inspection.cjs` 按设计保留巡检预约和付款节点，却又用 `cleanupBuyer()` 删掉了它们的交易订单，留下指向空订单的付款记录。
- **影响**：只影响开发库的数据整洁和“全库一致性核对”的读数，不影响产品。演练脚本自己用闭包清理，不留这类数据（场景 6 的核对限定在演练数据上是 0 违反）。
- **处理**：观察。`trade-smoke/lib.cjs` 不在这次允许改的文件里；建议另开任务让 `cleanupBuyer()` 一并删目标是这些订单的站内信，`inspection.cjs` 要么不删交易订单、要么连预约一起清。现有的 215 + 20 条可以在开发库里一次性清掉（不影响任何用例）。

## S6-04 账号冒烟脚本留下注册的号码和企业

- **现象**：开发库里有 14 个 `p-…` 验证码注册账号、2 个 `closed-…` 已注销账号、16 个“个人客户”机构和两家“冒烟测试物流”企业（UTC 2026-11-23 15:54–16:32，几次 `identity-account-smoke.cjs` 和 S5-8 的 E2E）。
- **根因**：`identity-account-smoke.cjs` 结束时只做 `cleanupBuyer()`，不删它注册的号码、个人客户机构、企业、验证码和导出文件。
- **处理**：观察。S6 场景 7 跑这个冒烟时由 `07-recovery.cjs identity` 在后面清掉了它这一次产生的 82 行（残留 0）；之前留下的没动（不是本次产生的）。建议给冒烟脚本加同样的清理。

## S6-05 巡检冒烟脚本按设计留下预约和 MinIO 对象
